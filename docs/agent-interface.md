# Using Surrounded by Slop with AI agents

An agent dropped into an unfamiliar repo has the same problem you do: it cannot
read its way to understanding, so it greps, guesses, and burns context. This
project's **agent interface** hands it a semantic graph instead — a ranked map
of what matters, and exact answers to "who calls this?".

Two surfaces, same core:

- **`sbs`** — a headless CLI. Every command prints plain text by default and
  canonical JSON with `--json`.
- **`sbs mcp`** — a Model Context Protocol server over stdio, exposing the same
  queries as native tools.

Everything runs locally. No network calls, no telemetry, nothing leaves the
machine — the MCP server speaks stdio, not HTTP.

## Quickstart

### Claude Code

```console
$ claude mcp add slop -- npx -y @surrounded-by-slop/cli mcp
```

Then point the agent at the graph once, so it reaches for it instead of grep:

```console
$ npx @surrounded-by-slop/cli init
```

`sbs init` writes a short block into `AGENTS.md` (creating `CLAUDE.md` with
`@AGENTS.md` if you have none). It is a **pointer, not a dump**: it names the
commands and stops. `sbs init --check` exits non-zero when the block is missing
or stale, so CI can guard it.

<!-- agent:init -->

```console
$ sbs init
created: AGENTS.md
created: CLAUDE.md
```

<!-- /agent:init -->

### Cursor / other MCP clients

Add the server to the client's MCP configuration:

```json
{
  "mcpServers": {
    "slop": { "command": "npx", "args": ["-y", "@surrounded-by-slop/cli", "mcp"] }
  }
}
```

### Codex, or any agent that can run a shell

No MCP needed — the CLI is the interface. Run `sbs init` so the agent knows the
commands exist, and it will call them like any other tool.

## Commands

Every command takes an optional path (default: the current directory) and
accepts the shared options below.

| Command | What it answers |
|---|---|
| `sbs map [path]` | "What is this repo?" — ranked, token-budgeted skeleton |
| `sbs query defs <pattern>` | "Where is this declared?" |
| `sbs query callers <symbol>` | "Who calls this?" (`--depth k` for transitive) |
| `sbs query callees <symbol>` | "What does this call?" |
| `sbs query importers <file>` | "Who depends on this file?" |
| `sbs query path <from> <to>` | "How does A reach B?" |
| `sbs query slice <symbol>` | "Show me this symbol's neighborhood" |
| `sbs impact` | "What does this diff put at risk?" |
| `sbs analyze [path]` | The whole Semantic Graph as canonical JSON |
| `sbs export --format <id>` | The graph as `mermaid`, `json`, `dot` or `plantuml` |
| `sbs mcp [path]` | Serve the queries over MCP (stdio) |
| `sbs init [path]` | Write the agent pointer block into `AGENTS.md` |

### Options

| Option | Applies to | Meaning |
|---|---|---|
| `--budget <tokens>` | `map` | Token budget for the map (default 2000) |
| `--depth <k>` | `callers`, `callees`, `slice`, `impact` | Hops to follow (impact: 2) |
| `--root <path>` | `query`, `impact` | Project root (default: cwd) |
| `--staged` | `impact` | Diff the staged index against `HEAD` |
| `--diff <ref>` | `impact` | Diff the working tree against a ref |
| `-` | `impact` | Read a unified diff from stdin |
| `--json` | most | Emit canonical IR JSON instead of text |
| `--include <glob>` | all | Replace the default include glob (repeatable) |
| `--exclude <glob>` | all | Add an exclude on top of the defaults (repeatable) |
| `--include-tests` | all | Analyze test files too (excluded by default) |
| `--format <id>` | `export` | `mermaid`, `json`, `dot` or `plantuml` — every layout-free format |
| `--check` | `init` | Exit 1 if the `AGENTS.md` block is missing or stale |
| `--verbose` | all | Print discovery notes to stderr |
| `--help` | all | Show usage |
| `--version` | — | Print the version and exit (also `-v`) |

## Exit codes

Scripted callers need to tell a quiet answer from a failed one, so the CLI
never returns 0 for a project it could not read:

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | The command failed (a bad diff, an unreadable file) |
| 2 | Usage error — unknown command or flag |
| 3 | Nothing analyzable was found: wrong path, filters too narrow, or a language this tool does not read |

Code 3 is the important one. An empty map that exited 0 would be
indistinguishable from a small repo, so `map`, `analyze`, `export` and
`query` refuse to answer at all when discovery found nothing, and stderr says
which of those causes applies.

## The map line grammar

`sbs map` output is normative: third-party tools can parse it. The format is
stable and deterministic — no timestamps, no absolute paths — so a committed
map diffs cleanly.

```
map      := header "\n" { file-block }
header   := "# repo map · " count " files · " count "/" count " symbols · deeper: `sbs query callers <name>`"
file-block := file ":" "\n" { symbol-line }
file     := project-relative path, POSIX separators
symbol-line := "  " kind " " name [ signature ] " ·" line [ " ←" inbound ]
kind     := "fn" | "method" | "class" | "interface" | "enum" | "const" | "ns"
name     := the declared symbol name
signature := the declaration's signature, when the analyzer has one
line     := 1-based start line of the declaration
inbound  := count of incoming calls + imports; omitted when zero
```

Reading it:

- **Two leading spaces** mark a symbol line; a line with none is a file header.
- **`·<line>`** is where the symbol is declared — jump straight there.
- **`←<n>`** is how many call/import edges point *at* this symbol. Higher means
  more load-bearing; absent means nothing in the analyzed set references it.
- **Ordering is meaning**: files and symbols are ranked by importance, so the
  first lines are the ones worth reading. Ties break deterministically (score,
  then source line; then id), never by traversal order.

Symbols are cut to fit `--budget` by keeping the largest prefix of the ranking
that fits, so a smaller budget is always a prefix-truncation of a larger one —
never a different selection.

For the full node/edge model behind these answers, see
[the IR spec](ir-spec.md).

## What each language actually knows

Precision differs per language, and the table below is generated from each
adapter's own capability flags — the page cannot promise more than the code
declares.

<!-- agent:languages -->

| Language | Files | Imports | Call graph | Control flow | Data flow |
|---|---|---|---|---|---|
| TypeScript / JavaScript | `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` | yes | resolved by the type checker | yes | yes |
| Python | `.py` | yes | heuristic — marked `confidence: "low"` | no | no |
| Go | `.go` | yes | heuristic — marked `confidence: "low"` | no | no |
| Java | `.java` | yes | heuristic — marked `confidence: "low"` | no | no |
| Rust | `.rs` | yes | heuristic — marked `confidence: "low"` | no | no |
| Ruby | `.rb` | yes | heuristic — marked `confidence: "low"` | no | no |
| C# | `.cs` | yes | heuristic — marked `confidence: "low"` | no | no |

<!-- /agent:languages -->

A `heuristic` call graph means edges are matched by name within a file, with no
type checker behind them: they are drawn dimmed, marked `confidence: "low"` in
the IR, and should be treated as leads rather than facts. TypeScript's call
graph is resolved through the compiler, so its edges are ground truth.

Every command above analyzes all of these: point `sbs map` at a Python, Go,
Java, Rust, Ruby or C# repo and it reads it, loading only the grammars that
repo actually needs.

Per-language specifics — Go's package-vs-file imports, Rust's `impl` blocks,
Ruby's metaprogramming blind spots, C#'s file-scoped namespaces — are listed in
the [user guide](user-guide.md#language-limits).

## Guarantees

- **Deterministic.** The same input produces byte-identical output: ids derive
  from what a thing is, never from traversal order, and every list is sorted.
  Maps and graphs are diffable in Git.
- **Local.** All analysis happens in-process. No network calls, no telemetry.
  `sbs mcp` speaks stdio, so nothing is served on a port.
- **Honest.** Where the analyzer is guessing, it says so — low-confidence edges
  are marked in the IR and dimmed in every export, rather than presented as
  resolved.

## Performance and token claims

**There are no numbers on this page yet, and that is deliberate.** Every tool
in this space advertises spectacular figures — "94% fewer tool calls", "10×
token cut" — usually unreproducible. Rule 2 says tested means tested, and that
applies to a marketing claim exactly as it applies to code.

So the harness exists first, and the numbers come from it or not at all.

### Methodology

`pnpm bench:agent` runs a committed gold question set through the same agent
twice:

- **Condition A** — plain repo access. The agent greps and reads.
- **Condition B** — the same agent, plus the `sbs` MCP server registered and
  the `AGENTS.md` bootstrap block present.

Both use the same model at temperature 0, and each question is run three times
by default (`--runs`). Per question the harness records:

| Measure | How |
|---|---|
| Correctness | Recall against a gold answer: does the reply name the symbols and files the graph proves are involved? Identifiers are matched on word boundaries, so `recharge` never counts as `charge`. |
| Tokens | Input + output + cache tokens from the agent transcript. Unmeasured means *unmeasured* — it is reported as such, never as zero. |
| Tool calls | `tool_use` blocks in the transcript. |
| Wall-clock | Seconds per question. |

The question set lives in
[`bench/agent-questions.json`](../bench/agent-questions.json) — 20 questions in
three families: *where-defined*, *who-calls*, and *what-breaks*, over
`examples/orders-app` and `packages/core`. Every expected answer is checked
against the real semantic graph by `node scripts/agent-eval.mjs --verify`, which
runs in CI and costs nothing, so the gold set cannot rot as the fixtures change.
Scoring is pure and unit-tested on canned transcripts, so the numbers are
reproducible from a transcript without an API key.

**The harness is not CI-gated**: it spends real API tokens, so it is a
maintainer tool, run deliberately before making or refreshing a claim. Results
are written to `bench/agent-results.local.json` with the date, model and commit.

Adding a question: give it a stable id, name a repo and a family, and list only
what the graph can prove.
